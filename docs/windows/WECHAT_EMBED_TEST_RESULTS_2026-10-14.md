- 注册表 ProductName 返回 Windows 10 Pro；它与上述构建信息不一致，记录原值，不据此断言实际系统品牌。CIM 系统查询因沙箱限制未成功。

- 探针：C# WinForms + Win32 API；Windows PowerShell 5.1 Add-Type 编译独立 WindowsApplication exe。
- v2 自检观察到探针和模拟窗口 DPI=120（125%），没有完成多显示器、其它 DPI 或不同 Windows 版本验证。
- 首个 PowerShell 原型部分状态只能通过程序日志观察；独立 exe 后可通过窗口列表及无障碍树确认界面。

## 2. 测试系统与实现范围

### 初始版本

官方 exe 路径设置、启动、候选窗口枚举、手动嵌入、恢复。
通过 SetParent 修改父窗口，改为 WS_CHILD、清除部分顶层样式，按容器尺寸调用 SetWindowPos。
GetParent 验证父级关系；恢复原父级、窗口样式与矩形。
同进程模拟自检发现恢复时的样式/父级顺序问题，调整为先恢复样式再恢复父级后通过。

### 第二版 v2

以 TableLayoutPanel 明确分隔顶部、微信容器、分析栏和状态栏，替换原 Dock 组合。
启动时尝试 Per-Monitor-V2 DPI，默认最大化，支持收起分析栏。
容器 Resize 以及 500 ms 定时器检查实际窗口矩形，尺寸或位置不匹配时校正。
附带 --selftest：模拟窗口的尺寸、区域交叠及恢复断言。
标题显示“微信嵌入可行性原型 v2 · 尺寸适配”。

尚未实现：自动绑定启动窗口、登录后新窗口跟踪、账号隔离、多账号 UI、焦点桥接、完整弹窗管理、OCR 与模型分析。
路径设置可用，但用户仍要手动刷新/嵌入，这不是最终产品流程。

原自检结果文本：


这是模拟窗口结果，不应移用为真实微信兼容通过。

## 5. 当前判断

“GetParent 成功”只证明窗口被重新托管。用户已经反馈单击和滚动异常，所以不能把窗口嵌入称为完整成功。
任务栏进入后恢复正常，使窗口激活、前台状态和焦点成为值得优先验证的假设；它不是根因证明。
还需排查微信顶层窗口假设、自绘渲染、样式变化、跨进程 DPI 重置与尺寸校正影响。
不能因双击有响应就认为消息区、滚轮、输入法都兼容。

微软资料提示：跨线程/跨进程窗口重设父级会关联输入队列，未按这种方式设计的窗口可能出现兼容问题。
- https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setparent
- https://devblogs.microsoft.com/oldnewthing/20130607-00/?p=4143

本次未 hook、未注入微信、未修改官方程序、未读取微信数据库、未上传聊天到模型。

## 6. 下一位 agent 的优先任务

1. 确认仅运行一个探针版本，使用测试账号，建立独立微信的单击、滚动、输入基线。
2. 同窗口嵌入后重复相同操作，记录异常；正常恢复后再次测试，明确任务栏操作恢复的是哪个窗口。
3. 在探针内部增加只包含元数据的诊断：前台/激活/焦点句柄、线程、父级、样式、DPI awareness、外框/客户区、尺寸校正次数。
4. 一次只变一个条件：暂停尺寸定时校正、焦点处理、样式处理分别做对照，不一次叠加多个猜测修复。
5. 校验原型与微信登录窗口、主窗口的 HWND/PID 切换，完成自动跟踪；多个候选不猜测账号归属。
6. 只有单击、滚动、输入法、弹窗及恢复通过后，才继续测试双账号同时在线。
7. 若跨进程托管始终不兼容，报告证据并与用户讨论联动排列等替代；不能静默把旁挂当成用户要求的内嵌。

验收必须记录独立基线、嵌入状态、恢复状态和未测项。不要重复声明“扫码、多开、输入法、弹窗均已通过”。
